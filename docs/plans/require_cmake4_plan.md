# Require CMake 4

**Status: Approved (2026-11-03), in progress.** Approved with one addition: the `ubuntu-dev` image is fixed as part of
this plan (D7, Step 1), because it cannot build the repo at CMake 4.0 and has to be fixed anyway. D1 to D6 stood.

Closes [flywheel-dag#57](https://github.com/tomlin256/flywheel-dag/issues/57).

## Problem

The issue reads: *"Upgrade to cmake 4. We are abandoning cmake 3."* It was opened a minute after
[flywheel-dag#56](https://github.com/tomlin256/flywheel-dag/issues/56), and the two ship as one release, v1.0.0
(decisions D1 and D2 of [that plan](require_cxx23_plan.md), approved). Step 7 of that plan, the release, waits for
this one.

Today the repo asks for CMake 3 in eleven files and carries code that exists only because of it:

- `CMakeLists.txt:20` and `tests/consumer/CMakeLists.txt:14` say `cmake_minimum_required(VERSION 3.20)`, the first
  CMake with `cxx_std_23`.
- Seven check scripts say 3.18 (`check_install`, `check_platform`, `check_tree_name`, `install_dependencies`), 3.19
  (`check_warning_flags`), 3.20 (`check_standard_guard`) and 3.21 (`check_presets`).
- `CMakeLists.txt:227` and `:230` set two policies, CMP0156 and CMP0179, that CMake 3.29 and 3.31 made NEW. Under a
  4.0 minimum they are NEW without being set.
- `tests/CMakeLists.txt:192` registers `test_presets` only for CMake 3.21 or later, and the comment over it counts
  3.19, 3.20 and 3.21.
- `README.md:229` says "CMake 3.20 or later" and `:234` says "They need CMake 3.21 or later".

The CMake each place runs today:

- **CI:** the runner images list CMake 4.4.4 (Ubuntu 26.04 image 20261026.180.1, macOS 26 and 15 images), with 3.31.5
  and 4.1.2 alongside. So CI should already run 4.4.4 against a floor of 3.20. I read that in the images' readme, not
  in a CI log; Step 3 makes the log say it.
- **This Mac:** Homebrew's 4.2.3.
- **The `ubuntu-dev` container:** apt's 3.28.3. It cannot configure the repo once the floor is 4.0, so Step 1 fixes
  its image.

### What I measured

Scratch copies of `3cbe749` (the repo was not touched) with every `cmake_minimum_required` set to 4.0 and the two
policy settings deleted, and nothing else edited. Configured, built and tested with CI's flags, `-Werror=dev
-Werror=deprecated -DFLYWHEEL_DAG_WARNINGS_AS_ERRORS=ON`, so a CMake or compiler warning is an error.

| CMake (source), compiler | Result |
|---|---|
| 4.0.7 (Kitware, the last 4.0 release), Apple Clang 21 | no CMake or compiler warning; ctest 42 of 42; benchmark invariants match |
| 4.2.3 (Homebrew, this Mac's), Apple Clang 21 | the same |
| 4.4.5 (Kitware, the newest; CI's image has 4.4.4), Apple Clang 21 | the same |
| 4.0.7 (Kitware, aarch64), GCC 13.3 in `ubuntu-dev` | the same |
| 4.4.5 (Kitware, aarch64), GCC 15.2 in the `ubuntu:26.04` image (CI's compiler) | the same |

Kitware's tarballs were checked against the SHA-256 file of their release. The Mac rows share one tree, configured by
each CMake in turn, oldest first, because a tree generated by a newer CMake cannot be configured by an older one.

- **The floor changes nothing that CMake generates.** Two copies of `3cbe749`, one as it is and one at the 4.0
  minimum without the policy settings, configured by the same CMake (4.2.3): 299 generated files
  (`compile_commands.json`, every `link.txt`, `flags.make` and `build.make`, `Makefile2`, `CTestTestfile.cmake`,
  `cmake_install.cmake`, `DependInfo.cmake` and the package config) are identical once the tree roots are
  normalized. So CMP0156 and CMP0179 NEW from the minimum are what the explicit settings gave, and no other policy up
  to 4.0 moves anything here. No benchmark measurement is needed.
- **CMake 3 is refused clearly, on the two routes that reach the engine's `CMakeLists.txt`.** CMake 3.31.12 prints
  `CMake Error at CMakeLists.txt:20 (cmake_minimum_required): CMake 4.0 or higher is required.  You are running
  version 3.31.12` for the engine as the top-level project, and the same line, at the engine's file, for a consumer
  whose own minimum is 3.20 and which pulls the engine in with `FetchContent`.
- **An installed package works under CMake 3.** A consumer built with CMake 3.31.12 against the package that
  CMake 4.2.3 installed configures, builds and runs (`tests/consumer`, in package mode). The package's targets file
  asks for `cmake_policy(VERSION 3.0.0...4.0)` and the engine's usage requirement for `cxx_std_23`, which 3.20 has.
- **The presets file must not say 4.0.** With `cmakeMinimumRequired` set to 4.0.0, `cmake --preset` on CMake 3.31.12
  stops before reading `CMakeLists.txt`, with `"cmakeMinimumRequired" major version 4 must be less than 3`, which does
  not say what to do. The file's own minimum is the CMake that can read a version 3 presets file, 3.21, and it stays
  there (D5); the user then reaches the line above.
- **CMake 4.4 spells the standard flag differently.** The same source gets `-std=gnu++2b` from 4.2.3 and
  `-std=gnu++23` from 4.4.5. The guard of flywheel-dag#56 reads `__cplusplus`, which is 202302L for both on Apple
  Clang and GCC 15.2, so nothing depends on the spelling.

## The change

```cmake
# 4.0 is the floor: this project is CMake 4 (flywheel-dag#57). It is a plain minimum, not a
# <min>...<max> range: a range flips every policy up to <max> to NEW, which needs its own audit.
# Every policy up to 4.0 is NEW here, including CMP0156 (a static library is listed once on a
# link line where the linker allows it, so Apple's ld stops warning "ignoring duplicate
# libraries" on every relink) and CMP0179 (the first occurrence is the one kept).
cmake_minimum_required(VERSION 4.0)
```

The two `if(POLICY …) cmake_policy(SET …)` blocks and their comment go, since the comment above now carries the
reason. The consumer project and the seven scripts say `cmake_minimum_required(VERSION 4.0)`, and the notes on their
lines about `string(JSON)` and `--list-presets` go with the versions that needed them. `tests/CMakeLists.txt` registers
`test_presets` without the 3.21 condition. The README says "CMake 4.0 or later", drops the sentence that the presets
need 3.21, and says what a consumer meets: adding the engine with `FetchContent` needs CMake 4.0 or later in your
project too, because the engine's own `CMakeLists.txt` asks for it, and an installed package asks only for 3.20, which
`cxx_std_23` needs.

`test_cmake_floor` (`tests/check_cmake_floor.cmake`, a `cmake -P` script like the other `check_*` scripts) holds the
floor to one number:

- the root `CMakeLists.txt` has a plain `cmake_minimum_required(VERSION X)`, and that is the floor;
- every other `cmake_minimum_required` in the checkout, outside `build*/` and `.git/`, is exactly that version, so
  neither a stale 3.x nor a range survives in the consumer project or in any script, now or in a script added later;
- `README.md` says "CMake X or later".

It fails if it finds no call in the root, so a wrong path cannot pass by checking nothing. It is registered at the top
level, where the checkout it reads is the engine's.

CI shows which CMake it runs, and tests the floor itself on Linux with Kitware's 4.0.7 (D3).

## Decisions to confirm

My defaults, each one a place to edit before approving.

- **D1. The floor is 4.0.** The issue says "cmake 4", not the CMake CI happens to have (4.4) or this Mac's (4.2).
  4.0.7 passes every test, so a consumer on any 4.x is not refused for no reason.
- **D2. `test_cmake_floor`.** Without it, the next script copied from another project brings its CMake 3 minimum
  back, and nothing notices. With it, there is one floor and a test that says so. I recommend it. Strike it and the
  Step 2 commit has no new test, only the README and the minimums.
- **D3. A CI leg for the floor.** CI runs 4.4.4, so a floor of 4.0 is otherwise only what I ran by hand. A third job
  on `ubuntu-latest` runs the same preset with Kitware's 4.0.7, from the release tarball, checked against a SHA-256
  that is in the workflow. It costs one more job per push and no third-party action. I recommend it. Strike Step 3's
  job and CI shows its CMake version only.
- **D4. The installed package does not refuse CMake 3.** Nothing in the package needs 4.0: it is headers, a targets
  file and a config that finds two dependencies, and a consumer on 3.31.12 builds and runs against it (above). A
  `FetchContent` consumer is refused, because the engine's `CMakeLists.txt` runs in its CMake; a `find_package`
  consumer needs 3.20, which `cxx_std_23` asks for. The alternative is a version check in
  `cmake/flywheel_dagConfig.cmake.in`, which would refuse a build that works.
- **D5. `CMakePresets.json` stays at version 3, `cmakeMinimumRequired` 3.21.** It says what CMake reads the file, not
  what the project needs, and a higher number turns a clear refusal into the confusing one above.
- **D6. The release is the joint v1.0.0, as flywheel-dag#56 decided.** This plan's last step runs Step 7 of that one.
- **D7. The `ubuntu-dev` image is fixed in this plan.** Added at approval. The image installs apt's CMake 3.28.3, so
  the container that builds this repo on Linux stops at the floor. The image is built from another repository, which
  gets its own issue and plan: Kitware's release tarball, pinned to 4.4.5 (what the runner images carry) and checked
  against a SHA-256 for each architecture, replaces apt's `cmake`, and the image's test asserts CMake 4 on arm64 and
  on the emulated amd64. The live container keeps 3.28.3 until it is recreated, which closes any shell open in it, so
  that stays your call. Until then my runs use Kitware's 4.0.7 in `~/.local` inside it, which is also the floor.

## Designs I rejected

- **`cmake_minimum_required(VERSION 3.20...4.0)`.** A range lets CMake 3.31 run the project, which is the opposite of
  the issue, and it flips every policy up to 4.0 on a CMake that knows them anyway.
- **A floor of 4.2 or 4.4.** That is what this Mac or CI happens to have. It refuses consumers on 4.0 and 4.1 for no
  reason the project has.
- **Keeping the two `cmake_policy(SET …)` blocks.** They are dead under the minimum, and the generated files are
  identical without them.
- **A CMake version check in the package config.** It would refuse a consumer whose build works (D4).
- **`pip install cmake==4.0.7` or a third-party action for the CI floor leg.** The tarball comes from the project
  that makes CMake, with a checksum in the workflow, and needs neither.
- **Raising the presets file to 4.0.0 or to a newer schema version.** The first makes CMake 3 users' refusal worse (D5),
  and the second buys nothing today.

## Not in this plan

- **CMake 4 features.** `CMAKE_COMPILE_WARNING_AS_ERROR` in place of the `-Werror` option, file sets, a newer presets
  schema and the like are candidates. Each is a design change with its own risk, so each gets its own issue after this
  lands.
- **Recreating the live `ubuntu-dev` container.** The fixed image reaches it only when `./start.sh --detach` recreates
  it, which closes any shell open in it, so that is left to you. Until then it keeps CMake 3.28.3, and the Kitware
  binary Step 1 puts in `~/.local` does the job.
- **A macOS CI leg for the floor.** The floor job is Linux only. The Mac was run by hand on 4.0.7 for this plan and
  again in Step 4.
- **Windows.** Not built or tested.
- **The older plans.** Their "CMake 3.18" assumptions were true when written.

## Self-review — risks and assumptions

- **The probes ran a throwaway flip of `3cbe749`, not the commit this plan produces.** Step 2 repeats them on the real
  commit, and Step 4 on the tip.
- **Policies introduced after 4.0 stay unset.** Under `-Werror=dev`, a CMake newer than the one that wrote the
  workflow could warn about one the project triggers, and CI would stop. That risk is unchanged by this plan: CI is
  green today with the same flag, against a 3.20 floor, on whatever CMake the images have.
- **CI's CMake is what the image readme says.** I read 4.4.4 there and have not seen it in a CI log. Step 3 prints it.
- **The floor job downloads at run time.** A GitHub outage fails that job and nothing else, and the checksum stops a
  changed file. I did not verify Kitware's GPG signature of the SHA-256 file, only the hash against the release's own
  file.
- **A `FetchContent` consumer on CMake 3 is refused, and an installed-package consumer is not.** That is deliberate
  (D4), and the README and the release notes say so.
- **The container.** The image is fixed, but the live container keeps CMake 3.28.3 until it is recreated, and nothing
  here warns whoever builds this repo in it before then except CMake's own refusal. The README's requirement line says
  4.0.
- **The image's repository is private and separate.** This plan names it without linking it: its issue and plan are
  there, and their commits are pushed there. The Kitware download it makes at image build time is the same one this
  plan's CI job makes at run time, so a checksum slip would fail in both.
- **Assumptions:** no CMake 4 feature is adopted; the suite keeps running under `ctest` with no sleeps; CI stays on
  GCC 15.2 and Apple Clang with the images' CMake; flywheel-dag#56's release decisions (D1 and D2 there) stand.
